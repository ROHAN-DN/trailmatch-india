# Fixes — 2026-08-05

The last two flagged-but-not-fixed items: the dependency vulnerabilities
and `failure_predicted`/`failure_criterion`. Both are now genuinely
addressed — the ones worth fixing are fixed and verified; the ones not
worth the risk are documented with real reasoning, not silently dropped.

## Dependency vulnerabilities — triaged by actual exploitability, not just severity label

Started at 23 vulnerable packages. Ended at 13 — every fix applied was
individually verified (type-check, full test suite, production build,
and for jsPDF specifically, a dedicated new test suite run before *and*
after the upgrade to confirm identical behavior), and every deferred item
has a specific, evidence-based reason, not just "seemed risky."

**Fixed:**
- `next-auth` (CRITICAL) 4.24.7 → 4.24.15, plus its transitive `cookie`
  and `uuid` fixes — same major version, safe.
- `@supabase/supabase-js` (LOW) → 2.112.0 — same major version, safe.
- `nodemailer` (HIGH) 6.9.14 → 9.0.4 — required going one version further
  than next-auth's declared peer range (`^7.0.7`); checked first that
  nothing in this codebase imports nodemailer directly (only next-auth's
  `EmailProvider` uses it internally, for magic-link sign-in emails), and
  that its core `createTransport`/`sendMail` API — the only surface
  next-auth actually touches — has been stable across these versions.
  Verified via full build + test suite; real SMTP delivery itself
  couldn't be tested (no real credentials in this sandbox) — flagged as
  the one honest gap in this specific fix's verification.
- `jspdf` (CRITICAL, 12 advisories including a 9.6 CVSS HTML-injection
  issue) 2.5.1 → 4.2.1. Checked `lib/pdf.ts`'s actual API usage first —
  confirmed it only uses the most basic surface (text/color/rect/pagination,
  no forms, links, or AcroForm), which is exactly what most of the 12
  advisories don't touch. Wrote a real test suite for `lib/pdf.ts` first
  (there wasn't one) — valid-PDF-header checks, embedded-content checks,
  multi-page and adversarial-input handling — ran it against 2.5.1 to
  establish a baseline, then against 4.2.1 to confirm identical behavior.
  Also resolves `dompurify`'s vulnerability (a jsPDF transitive
  dependency).
- `elliptic` (CRITICAL, private-key-extraction) — actually fixed last
  session, included here as it's part of the same audit's before/after
  count.

**Deliberately not fixed, with reasoning:**
- `vitest`/`vite`/`vite-node`/`esbuild` (the remaining CRITICAL) — every
  one of these advisories requires a network-listening dev/UI server
  (`vitest --ui`, or a Vite dev server) to be actively running. Confirmed
  `package.json`'s own test script is `vitest run` — headless, one-shot,
  never any server — the only invocation used anywhere in this entire
  engagement. The fix path is a 3-major-version jump (1.6 → 4.1) that
  would risk breaking the verification infrastructure everything else in
  this project depends on, for a vulnerability class this project's
  actual usage never exposes.
- `next` itself (HIGH, ~20 real advisories including SSRF and DoS vectors)
  — genuinely the most significant remaining item, and flagged as the
  single highest-priority one for whoever continues this project. Not
  attempted: the fix requires a 14→15/16 major-version framework
  migration with real breaking changes (async request APIs, React 19),
  affecting a codebase with ~40 API routes — this needs its own dedicated
  migration effort, not a fold-in to a dependency-cleanup pass. Checked
  specifically whether the HIGH-severity middleware-bypass advisory
  (relevant given `middleware.ts` now enforces MFA) applies here — it
  requires i18n routing, which `next.config.js` doesn't configure, so
  that specific vector doesn't reach this app; the framework's broader
  security debt remains real regardless.
- ESLint tooling (`eslint-config-next`, `@typescript-eslint/*`, `glob`,
  `minimatch`) — dev-only, never shipped, version-locked to Next.js
  itself; deferred alongside the `next` upgrade rather than attempted in
  isolation.

Final count: 13 vulnerable packages (1 critical, 9 high, 2 moderate, 1
low) — down from 23, with every remaining one specifically triaged rather
than left unexamined.

## `failure_predicted` / `failure_criterion` — built properly this time

Migration 012's own comment scoped this as "set by nightly job"; migration
022 (last session) deliberately left it unbuilt, reasoning that a naive
version — flagging any screen-failure with any unmet/partial criterion as
"predicted" — would be almost always true and not meaningfully
informative, risking false confidence in a future accuracy analysis.

Built a real version instead: `pg_trgm` lexical similarity (already
enabled by migration 005, no new extension) between the coordinator's own
`screen_fail_reason` text and each unmet/partial criterion's description,
only flagging a prediction when the best match clears a real threshold.

**The threshold (0.15) is empirically calibrated, not guessed** — tested
directly against real Postgres before picking a number. Genuinely
correlated pairs ("eGFR too low at screening" vs "eGFR >= 45", "still on
metformin, did not stop in time" vs "No current use of metformin") scored
0.15–0.25. Genuinely unrelated pairs ("patient moved out of the city" vs
"eGFR >= 45") scored exactly 0. Short/generic reason text with real
false-positive risk ("not eligible", "no show", "coordinator error")
scored 0–0.09 against unrelated criteria. 0.15 sits with real margin on
both sides of that split.

**Stated honestly in the migration itself**: this is lexical similarity,
not clinical reasoning. "Declined due to renal function" scored 0 against
"eGFR >= 45" in calibration, despite the real clinical connection — trigram
similarity has no concept of that relationship. This will only catch
cases where a coordinator's own wording actually overlaps with the
criterion's, which is a real and common case, but a conservative, honest
subset of true correlations — missing a real one (false negative) is the
deliberately preferred failure mode over inventing a correlation the data
can't support, the same principle `lib/eligibility-rules.ts` already
applies to patient eligibility itself.

Verified against real Postgres with three scenarios in one run: a
correlated screen-failure (correctly flagged, correct criterion named), an
uncorrelated one (correctly not flagged), and a non-screen-failed outcome
(correctly `NULL`, not `false` — "not applicable" is a different fact than
"checked and found nothing"). Also confirmed `v_criterion_failure_rates`
— the aggregate view this entire feature exists to feed — now produces
real, non-empty, correct output for the first time since it was created.
