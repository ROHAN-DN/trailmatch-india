## 1. Match-jobs/month cap — actually built this time

Diagnosed last session, never implemented. `lib/plans.ts`'s trial tier
advertises "5 match jobs/month"; nothing checked it.

While wiring this up, found something bigger: `organizations.max_patients`/
`max_users` column DEFAULTS (`50`/`5`, from `schema.sql`) never matched
`PLANS.trial`'s advertised numbers (`10`/`2`), and nothing at org-creation
time (`pages/api/auth/[...nextauth].ts`'s "New user" branch) set these
explicitly — every self-signup organization silently got several times the
advertised free-trial capacity, for its full lifetime on that plan.

Also found `pages/api/billing/webhook.ts` had its own hardcoded duplicate
of the plan-limits object, completely separate from `lib/plans.ts` — two
sources of truth that could silently drift (the same class of bug as the
audit_log/columns issue from an earlier session).

**Fixed together**: added `max_match_jobs_per_month` to `Plan` and to
`organizations` (migration `020_match_job_limits.sql`, which also corrects
the wrong column defaults); org creation now sets all three limits
explicitly from `PLANS.trial` (the real fix; the corrected defaults are a
backstop); `syncOrgPlan` in the webhook now derives from `PLANS` instead of
its own copy; new `checkMonthlyMatchJobLimit()` in `lib/gate.ts`, wired
into `pages/api/match/index.ts` right after the existing rate limit check.
13 tests in `gate.test.ts` (9 existing + 4 new). Migration re-verified
against real Postgres from a fresh database.

## 3. `MEDICATION_CLASSES` — expanded from one entry to eight

Was deliberately kept to a single class (`potassium_sparing_diuretic`) out
of genuine epistemic caution — the file's own comment said as much. Expanded
using standard, stable pharmacology classifications chosen specifically for
being common real-world trial exclusion-criterion patterns: `loop_diuretic`
(the direct complement to the existing class), `nsaid`, `anticoagulant`,
`statin`, `ace_inhibitor`, `oral_corticosteroid`, `immunosuppressant`. Each
drug list is the standard generic-name roster for that class. Matching
`RXCLASS_NAME_HINTS` entries added for each, using single distinctive stems
where possible (`immunosuppress`, `anticoagul`, `nonsteroid`) to reduce
brittleness against RxClass's real, unverified exact formatting. 9 new
tests.

## 4. Two-call, patient-data-minimized extraction — the biggest piece

This project's own Tier 1 disclosure named this directly: "the patient
block and the residual trial text are still in the same call... splitting
those into two calls... was proposed a few turns back and never built."
Built this session, carefully — this is the single riskiest change made
in this engagement, since it restructures the most tested, most
business-critical function in the codebase (`scoreWithClaude`), which had
already had two production-breaking bugs found and fixed in it this month.

**The split**: Call 1 (new, `extractResidualCriteriaViaClaude`) has no
`Patient` parameter anywhere in its function signature — not a convention,
a structural guarantee that patient data cannot reach this prompt, because
there is none in scope to put there. Only invoked for trials that are a
genuine cache miss with real residual text after the rule-based pass —
increasingly rare over time as the trial-criteria cache (built two sessions
ago) fills up, since its output is cached immediately. Call 2 (the
existing prompt, simplified) never asks the model to extract anything —
every trial's criteria are fully known by the time it runs, either from
cache or from Call 1 moments earlier — so every trial gets the same
"already known, final" framing that previously only applied to cache hits,
and the `structuredCriteria` field is gone from its schema entirely.

**Correctness, not just the split itself**: caught a real bug in my own
first draft before running anything — Call 1's extraction results were
being looked up by exact `nctId` string match, but Claude can echo the ID
back with different case/whitespace than the canonical trial object has,
which would have silently dropped extraction results for any trial where
that happened. Fixed with the same normalized-ID matching this file
already uses elsewhere for exactly this reason, before ever running a
test.

**Test impact, handled systematically**: virtually every existing test in
`matcher.test.ts` implicitly relied on exactly one Claude call per match —
splitting into two calls broke 17 of the 30 tests in that file (mostly
`TypeError: Cannot read properties of undefined` from a second,
now-unmocked call). Went through every one individually: added a new
`claudeReturnsExtraction()` mock helper, moved `structuredCriteria` out of
the scoring-response fixtures into dedicated extraction-response fixtures
wherever a trial's text genuinely has residual content, added a second
trial fixture (`templatedTrialWithResidual`) for the tests that
specifically need to exercise Call 1 without disturbing the tests that
correctly rely on Call 1 never running for fully rule-based-parseable
text, and rewrote one test whose original premise (Call 2 "disobeying" a
do-not-extract instruction) is now structurally impossible — Call 2's
schema doesn't have the field to disobey with anymore — into a test of
what actually replaced that guarantee.

All 30 tests in `matcher.test.ts` pass; all 218 across the full suite pass.
