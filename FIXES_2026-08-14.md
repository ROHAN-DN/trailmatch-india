# FIXES_2026-08-14.md

Found during the user's first real `vercel --prod`/`npm run build` attempt
— genuinely new, not caught by anything in this engagement before now,
because every build I'd run myself always had placeholder environment
variables set. This is exactly the value of a real deploy attempt: it
exercises a state (zero env vars configured) that my own testing
methodology never had.

## The bug

`next build` failed outright during "Collecting page data":
```
Error: supabaseUrl is required.
  at <unknown> (lib/supabase.ts:4:25)
```

`lib/supabase.ts` had a top-level, eagerly-evaluated Supabase client:
```ts
export const supabase = createClient(
  process.env.NEXT_PUBLIC_SUPABASE_URL!,
  process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!
)
```
`@supabase/supabase-js` throws synchronously if the URL is empty.
Confirmed by grepping every one of the 33 files that import anything
from this module: **all 33 import only `supabaseAdmin`** (the
already-lazy factory a few lines below), never `supabase`. But
importing anything from a module runs the whole file top-to-bottom, so
this unused client still fired on every import, unconditionally.

## It wasn't just one file

Fixing `lib/supabase.ts` and rebuilding surfaced the same pattern
again, immediately, in a completely separate file:
`pages/api/auth/[...nextauth].ts` had its own **independent** eager
`createClient(...)` call — a duplicate of what `supabaseAdmin` already
provides correctly, not sharing the same module at all.

Rather than fix these one crash at a time as the build revealed them,
searched systematically for every top-level SDK instantiation reading
`process.env` directly across the whole codebase, then checked each
SDK's actual behavior with a missing key by testing directly (not
assumed):

| Location | SDK | Throws on missing key? | Action |
|---|---|---|---|
| `lib/supabase.ts` | `@supabase/supabase-js` | **Yes** | Removed the unused eager client entirely |
| `pages/api/auth/[...nextauth].ts` | `@supabase/supabase-js` | **Yes** | Replaced its own duplicate client with the shared, already-lazy `supabaseAdmin()` |
| `lib/email.ts` | `resend` | **Yes** — confirmed directly: `new Resend(undefined)` throws "Missing API key" | Converted to a lazy `resendClient()` factory |
| `pages/api/team/index.ts` | `resend` | **Yes** (same SDK) | Same fix |
| `lib/matcher.ts` | `@anthropic-ai/sdk` | No — confirmed directly, constructs fine with `undefined` | No change needed |
| `lib/stripe.ts` | `stripe` | No — confirmed directly | No change needed |
| nodemailer | — | Never called directly anywhere; only configured (lazily) inside next-auth's own `EmailProvider` | No change needed |

Two SDKs (`@supabase/supabase-js`, `resend`) throw eagerly on missing
credentials; two (`@anthropic-ai/sdk`, `stripe`) don't. This wasn't
guessed — each was tested directly with `node -e`.

## Verification

Re-built twice, deliberately testing both real scenarios rather than
just one:
```
env -i npx next build     → succeeds, all 44 routes, ZERO env vars set
                              (the actual state of a first deploy,
                              before Vercel's project env vars exist)
npx next build             → succeeds, placeholder env vars set
                              (this engagement's usual test method)
tsc --noEmit                → clean
vitest run                  → 267/267 passing, unchanged
node scripts/security-audit.js → 9/9 passed
```

## The real lesson

Every build I ran myself throughout this entire engagement used
placeholder environment variables, because that's what let me verify
the *rest* of the app. That same habit is exactly why this specific
failure mode was invisible to me — it only exists in the gap between
"no env vars at all" and "env vars set." The user's actual deploy
attempt tested a real condition my own process never had. Worth
remembering going forward: a clean build with placeholders configured
is not the same claim as a clean build with nothing configured, and a
real first deploy will always start at the latter.
