# Fixes — 2026-07-28

Continuation of the audit in this session's earlier message. Two things applied
first (the confirmed-critical DB bugs), then #5–7 from that audit investigated

## Applied first — the two critical DB bugs

**`enrollment_monitor_tasks_match_result_id_key`**: `ADD CONSTRAINT IF NOT EXISTS`
isn't valid PostgreSQL syntax — replaced with a `DO` block checking
`pg_constraint` first (same idempotent intent, valid syntax). Re-verified
against real Postgres: built real rows, ran the exact `UPDATE match_results
SET status='done'` the app runs on every match completion — it now succeeds,
the trigger correctly creates the monitor task row, and re-running the same
transition doesn't duplicate it.

**`upsert_site_profile()`**: was explicitly inserting into
`institution_city_key`, a `GENERATED ALWAYS AS (...) STORED` column — Postgres
never allows that, on any deployment. Removed it from the INSERT (Postgres
computes it). Re-verified: two calls for the same institution now correctly
insert-then-update (same UUID, merged specialties, `GREATEST(active_trials)`)
instead of crashing on the first call.

## A correction to last session's findings

I'd claimed `withinLimit`/numeric plan caps were "entirely unenforced." That
overstated it — `lib/gate.ts` has a second function, `checkLimit()`, that I'd
missed, and it genuinely does enforce `max_patients` for single-patient
creation. The real, narrower gaps (below) are what actually needed fixing.

## Batch-import and team-invite plan-limit gaps

**Batch patient import bypassed `max_patients` entirely.** The single-patient
path enforces it; the `if (req.body.batch)` branch (up to 20/call, callable
repeatedly) didn't. Fixed by computing how many of the batch's `patient_code`s
are genuinely new (excluding rows that are actually updates to existing
patients via the upsert) and checking that count against the plan limit in one
call. `checkLimit()` generalized to accept an `additionalCount` parameter
(defaults to 1 — every existing single-item call site is unaffected; verified
`current + 1 <= limit` is exactly equivalent to the original `current < limit`).

**`max_users` was never enforced anywhere.** Two fixes: an early check in
`pages/api/team/index.ts`'s invite handler (best-effort — gives the admin
sending the invite immediate feedback), and the real enforcement point in
`pages/api/auth/[...nextauth].ts`'s `signIn` callback, which is the only place
an invited user's actual `users` row gets created. Without the second one, the
first is cosmetic — an org could still exceed its cap if invites were accepted
after other members were added or after a plan downgrade.

9 new tests for `checkLimit`, covering the original single-item behavior
(unchanged), the new `additionalCount` behavior, and unlimited (`-1`) plans.

## CTRI — deeper than a fragile proxy

Investigated why CTRI matching is fragile, not just accepted it. Found
something bigger than the proxy dependency: fetching CTRI's real, live
"Trial Search" page directly (outside this app) shows a mandatory CAPTCHA —
"Security Code" + image challenge — which a bare GET request, like the one
this app makes, can never satisfy. The live site's URL structure is also
organized under `/Clinicaltrials/*.php`, not the bare `/Clinicaltrials.php`
this app requests, a sign this specific endpoint may predate a CTRI site
upgrade referenced on their own site.

Deliberately did **not** rewrite the scraping URL — guessing a replacement
without being able to verify it end-to-end against the real site would trade
one unverified assumption for another, the exact mistake this whole audit is
about avoiding. What's fixed instead: `fetchCTRI` now detects a CAPTCHA/
challenge-page response and reports it as an honest `status: 'error'`, instead
of silently falling through to row-parsing (finding zero rows, indistinguishable
from CTRI genuinely having no matching trials). One new test locks this in.
Flagged in the code as the single highest-priority Tier 2 item for CTRI —
this needs hands-on re-verification against the live site before CTRI results
should be trusted in production.

## Rate limiter — now actually enforced across instances

`lib/ratelimit.ts` was an in-memory `Map`, honestly self-documented as a
"Phase 1... accepted tradeoff" that doesn't hold across Vercel's multiple
serverless instances. Replaced with a Postgres-backed limiter — new migration
`019_rate_limits.sql` adds a `check_and_increment_rate_limit()` function that
does the whole "is this window current, should this request count or get
rejected" decision as one atomic `INSERT ... ON CONFLICT ... RETURNING`
statement, not a read-then-write from application code (which would have its
own race).

Verified this isn't just correct when called sequentially: fired 20 genuinely
concurrent Postgres connections at the same key with a limit of 10 — exactly
10 allowed, exactly 10 blocked, final count exactly 20 (zero lost updates from
a race). All 4 real call sites (`match`, `patients`, `abdm/initiate`,
`feasibility`) updated for the now-async API. Fails open (allows the request,
logs a warning) if the rate-limit check itself errors — a secondary
abuse-prevention layer being briefly unavailable shouldn't take the whole
product down; primary defenses (auth, RLS, the plan-limit fixes above) still
hold regardless. 9 new tests, plus the concurrency guarantee already verified
directly against Postgres.

## Serverless timeout risk (batch matching) — quantified, not yet changed

Did not implement a fix here. `pages/api/match/index.ts` processes up to 20
patients with a plain sequential `for` loop inside one request (correctly
using `waitUntil()` + `maxDuration: 300`, a sound choice for Vercel Pro).
Reasoned-through arithmetic: a single patient's match involves concurrent
CTgov+CTRI+RxNorm fetches (bounded by the slowest — likely CTRI, several
hundred ms to a couple of seconds through the proxy) plus one Claude call
(`max_tokens: 4000`, no streaming, realistically several seconds, more under
retry) plus PDF/upload/DB writes. Twenty of these run one at a time. At a
plausible ~10s per patient this fits inside 300s with room to spare; at a
less generous ~15s (a few patients hitting Claude retries) it's close enough
to the ceiling that it deserves real load testing, not just estimation, before
relying on it at full batch size in production.

Not fixed because: this is the single most business-critical code path in the
app (the one this session already found two production-breaking bugs in), it
has zero existing test coverage at the route-handler level (nothing in this
project tests `pages/api/*` directly — an established boundary, not an
oversight), and a concurrency change here has real correctness subtleties
(atomic progress-counter updates, per-patient failure isolation, interaction
with the final batch-complete notification) that deserve dedicated review
rather than being rushed in at the end of an already-large session. Left as a
clearly reasoned, quantified recommendation rather than an untested change to
the most sensitive part of the codebase.
