## `match_accuracy_events` — fixed precisely, not rebuilt from scratch

Before touching anything, checked what already existed rather than
assuming a whole new coordinator UI was needed. Found something
important: a DB trigger from migration 012 (`record_match_accuracy_event`,
`AFTER UPDATE OF enrollment_status ON match_results`) already existed, and
a complete, working coordinator-facing UI already existed too
(`components/EnrollmentStatusDropdown.tsx` + `pages/api/match/[id].ts`'s
PATCH handler) — both real, both in production code, neither previously
verified against each other.

Verified directly against real Postgres: inserted a realistic
`match_results` row (shaped exactly like what `lib/matcher.ts` actually
produces) and ran the exact `UPDATE` the coordinator dropdown performs.
The trigger genuinely fires and genuinely inserts a row — `outcome`,
`screen_fail_reason`, and `nct_id` all populate correctly. Only
`criteria_at_match` was broken: the trigger reads
`NEW.matches->0->'eligibilityDetails'`, a field nothing in this codebase
has ever written (confirmed earlier this engagement — declared on the
type, read in two places, never set anywhere).

**Fix**: migration `022_fix_match_accuracy_criteria.sql` replaces the
trigger function to read from `deterministicResults` (the field that's
actually populated on every real match) instead, mapping
`PASS→met, FAIL→unmet, UNKNOWN→partial` — the exact mapping the original
schema's own comment already documented as the intent. Re-verified with
the identical real-Postgres test: `criteria_at_match` now correctly
contains the real per-criterion status.

**Deliberately not built**: `failure_predicted`/`failure_criterion`
("set by nightly job" per the original schema comment, no such job
exists). A naive version — flagging any screen-failure with any
unmet/partial criterion as "predicted" — would be almost always true and
not meaningfully informative, and could mislead a future accuracy
analysis into false confidence. Left as real, separate, correctly-scoped
future work rather than building a low-quality version of it now.

## MFA for privileged roles — built

TOTP-based (no new delivery dependency — this project already depends on
Gupshup and Resend, both third-party services with their own failure
modes; TOTP needs neither). Required for `owner`/`admin` roles
specifically — the roles that can manage team members, billing, and org
settings, matching this project's own Tier 4 disclosure.

**Verified the actual library API empirically before writing any code
against it** — `otplib` v13 turned out to be a complete API rewrite from
the `authenticator` object most tutorials and older versions describe.
Caught this by testing directly against the installed package rather than
assuming, which also surfaced that v13 has genuine, native replay
protection (`afterTimeStep`) — verified with a real generated code, real
verification, and a real rejected replay attempt, before relying on it.

**`lib/mfa.ts`**: TOTP generation/verification, AES-256-GCM secret
encryption at rest (Node's built-in crypto, no new crypto dependency,
consistent with how `lib/fidelius.ts` already handles this project's other
real cryptography), and single-use backup/recovery codes (SHA-256 hashed,
constant-time comparison against every stored hash rather than a
short-circuiting loop, to avoid a timing side-channel). 29 tests,
including real TOTP round-trips (not mocked) and the actual replay-attempt
rejection.

**Migration `023_mfa.sql`**: five new columns on `users` — encrypted
secret, hashed backup codes, the last-consumed TOTP time step (what makes
replay protection durable across separate requests within one login
session), enrollment timestamp, enabled flag.

**Four API routes** (`pages/api/mfa/{setup,verify-setup,verify,disable}.ts`):
two-step enrollment (generate → confirm with a real code before actually
enabling, so a QR scan that silently failed can't leave someone locked
into unusable MFA), step-up login verification (TOTP or backup code),
and disable (requires a currently valid code — this app has no password to
re-check with, Google OAuth / magic-link only, so proving current
possession of the authenticator is the equivalent re-authentication step).

**Enforcement — layered deliberately, not just added to one place**:
counted first — 13 routes use the shared `lib/api-handler.ts` wrapper, 20
more have their own inline `getServerSession` calls. Asking a security
control to depend on 20+ individually-updated files being consistent is a
real risk of one being missed. Built `middleware.ts` as a universal,
JWT-only fast-path covering every route (pages and API alike) — new file,
this project had no middleware before. `withApiHandler` also gained its
own fresh, DB-backed check for the 13 routes that already go through it,
which stays correct even if the JWT-baked role snapshot goes stale
mid-session (documented, bounded tradeoff — see `middleware.ts`'s own
header comment for the full reasoning). Caught a real lockout bug in my
own first design before shipping it: a blanket "block until verified"
check would have made the MFA setup/verification routes themselves
unreachable by the exact unverified session that needs to call them —
fixed with an explicit `skipMfaCheck` exemption for three of the four
routes (not `disable.ts`, which correctly requires already being
verified).

**UI**: `components/MFASettingsCard.tsx` (enrollment/disable, added to the
existing `SettingsPanel`) and `pages/auth/mfa-challenge.tsx` (where
`middleware.ts` redirects an unverified privileged session — branches
between forced enrollment and step-up verification based on the fresh,
session-callback-derived status, not the JWT's stale snapshot). Caught and
fixed a sloppy placeholder in my own first draft (a dead dynamic import
and a no-op fetch standing in for next-auth's real session-update
mechanism) before it shipped — replaced with the actual `update()` call
from `useSession()`.
