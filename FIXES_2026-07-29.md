## CTRI matching — a real second attempt, with its uncertainty made visible

Last session added CAPTCHA/challenge-page detection to the existing
search-scrape — honest, but didn't fix the underlying problem: the live
CTRI search form requires a CAPTCHA a bare GET request can never satisfy.

This session went further. Research (documented in-repo, in this file and
in code comments) surfaced three real candidate paths, none of which are
verifiable from this sandbox (ctri.nic.in is not reachable here at all —
not from the app's own network, not from the research tools used to
investigate it):

1. **CTRI's own bulk-export endpoint** — already referenced in
   `scripts/seed-site-twins.ts` for a different purpose
   (`ctri.nic.in/ctri/Utils/exportData.php?Id=all&stype=full`), never
   wired into actual trial matching, never verified either. Architecturally
   this is the most promising lead: export endpoints are typically not
   CAPTCHA-gated the way interactive search forms are.
2. **WHO's ICTRP** (CTRI feeds it monthly) — real, but its live search
   portal disallows automated access in its own `robots.txt` (confirmed by
   hitting that block directly), and its real-time API requires a formal
   paid partnership with WHO. Its bulk CSV export exists but is distributed
   through an authenticated, 10-day-expiring OneDrive link — not a stable
   URL a server can fetch on a schedule. This path needs a business
   relationship or a recurring manual step, not code — not pursued further
   this session.
3. **The existing CAPTCHA-gated scrape** — kept as a fallback, unchanged.

**What got built**: `fetchCTRI` now tries the bulk-export endpoint first,
and only falls back to the search-scrape if that doesn't produce
trustworthy data. New module `lib/ctri-bulk-export.ts` holds the parsing
logic, kept deliberately separate and pure (no I/O) so it's directly
testable.

**The honest part, worth being explicit about**: the exact column
structure of a real CTRI export file has never been seen — there was no
real file available to verify against, and the endpoint itself has never
been reached. Rather than guess at exact header names and hope, the
parser does alias-based, case/punctuation-insensitive column matching
(built from column names an earlier session already guessed for a
different script, plus the WHO Trial Registration Data Set's own
authoritative 24-item field vocabulary — confirmed directly from
who.int, since every primary registry including CTRI is required to
report against it). It only trusts a response as real data when it
structurally looks right (`looksValid`) — both core fields present
(trial ID, title) AND at least one row with a real CTRI-ID-shaped value,
not just "the HTTP request succeeded." Anything else reports exactly
which fields it couldn't map and falls through to the scrape, so a real
deployment makes it immediately observable which strategy is actually
working — rather than silently guessing and shipping false confidence.

This can't regress current behavior: if the bulk export never works, the
system behaves exactly as it did before this session (falls through to
the scrape, which still has the CAPTCHA detection). If it does work, CTRI
matching goes from "very likely broken" to "the complete registry,
without depending on a CORS proxy or HTML scraping at all."

13 tests for the parser (constructed representative CSVs, explicitly
labeled as not verified against a real download — covering both the
legacy-style headers and a completely different WHO TRDS-style header
set, to prove the alias matching actually generalizes rather than only
working for one guessed schema) plus 3 integration tests through
`matchPatient` proving the orchestration itself: bulk export succeeding
skips the scrape entirely, bulk export failing correctly falls back, and
both failing produces one combined, honest error.

**What's still true and unresolved**: this cannot be marked "fixed" with
confidence — only "a real, defensively-built attempt has been made, and
its own success or failure will be immediately visible in production
logs the first time it runs against the real internet." That first real
run against ctri.nic.in is the only thing that can actually settle this,
and nothing in this sandbox can perform it.
