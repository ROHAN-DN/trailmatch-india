# TrialMatch India — Fix Pass, 11 July 2026

Base: `trialmatch-india-v10-final.zip`, confirmed via file-list diff to be a
strict superset of every other candidate zip (phase2-final, phase2-production,
checkpoint) before any of this work started.

Every fix below was verified by actually running a tool, not by inspection
alone. The three verification gates used throughout:

```
npx tsc --noEmit -p tsconfig.json          # main app type-check
npx tsc --noEmit -p tsconfig.scripts.json  # seed scripts type-check
npx vitest run                              # new test suite
npm run build                               # full Next.js production build
```

All four now pass cleanly. None of them did when this pass started — the
codebase would not have completed `next build`, let alone run correctly in
production.

## 1. Fabricated trial fallback removed (`lib/matcher.ts`)

**The issue:** when both ClinicalTrials.gov and CTRI returned zero results,
the code asked Claude to *"Generate 4 realistic, medically accurate example
trials... Mark source as AI-Synthesised."* That tag was never checked
anywhere in the UI — `BatchPanel.tsx` and `MatchExplainability.tsx` render
every match identically regardless of `source`. A coordinator could receive
a fully fabricated trial (fake NCT ID, fake sponsor, fake eligibility) with
a "STRONG MATCH" badge and no way to tell it wasn't real.

**The fix:**
- The fabrication instruction is gone. When zero trials are retrieved, the
  matcher returns an honest empty result instead of calling Claude at all.
- Every fetch now reports real status (`'ok' | 'error'`), not just an empty
  array — so "we couldn't reach the registry" is distinguishable from "we
  checked and there's genuinely nothing right now." Both are shown honestly
  in `result.summary`, and structurally in the new `sourceStatus` field.
- If exactly one source fails, the result still includes real matches from
  the source that worked, prefixed with a deterministic (not model-authored)
  disclosure: *"Note: CTRI (India registry) could not be reached during this
  search — results below are from ClinicalTrials.gov only."*
- **Defense in depth**: even with the prompt instruction removed, a
  post-parse filter now drops any match whose `nctId` doesn't correspond to
  a trial that was actually retrieved, before it can reach the caller. This
  doesn't rely on the model behaving — it's enforced in code. Verified by a
  test that feeds a fabricated `nctId` through a mocked Claude response and
  asserts it's dropped (`lib/__tests__/matcher.test.ts`).
- `TrialMatch.source` is now the strict type `'ClinicalTrials.gov' | 'CTRI'`
  instead of `string` — this alone would make a reintroduced
  `'AI-Synthesised'` literal fail to compile.

**UI changes** (`BatchPanel.tsx`, `MatchExplainability.tsx`):
- A visible amber banner appears in the expanded match view whenever a
  source failed, naming which one and that it's a live-search gap, not a
  rejected match.
- A small ⚠️ indicator appears in the collapsed row so a coordinator
  scanning a batch of results doesn't have to open every row to notice.
- Each match card now shows a CTRI/ClinicalTrials.gov source badge — safe
  to add now that fabricated sources can't occur.
- An empty match list now shows a one-line explanation instead of rendering
  nothing.

**DB change** (`supabase/migrations/014_security_fixes.sql`): added
`match_results.source_status jsonb` to persist this per match run.

**Verified by:** 5 new tests in `lib/__tests__/matcher.test.ts` covering:
both sources failing, both succeeding with zero results, one failing with
the other returning real matches, a fabricated `nctId` being dropped, and a
normal fully-verified match passing through untouched. All 5 pass.

## 2. `SponsorPortal.tsx` didn't actually compile

**The issue:** lines 536–621 were an orphaned duplicate of code that
already existed correctly at lines 368–535 (an older draft of
`ProtocolUploadForm`'s save/parse logic, referencing a `parseWithAI`
function that doesn't exist in that scope) — left outside any function
after the real component's closing brace. This produced two fatal
`TS1128: Declaration or statement expected` parse errors.

**Why this matters beyond "it's a type error":** confirmed by testing the
original, completely unmodified `v10-final` build — `next build` fails
outright on this before reaching any other file. This was never going to
deploy as shipped, regardless of anything else in this list.

**The fix:** deleted the orphaned duplicate block (86 lines). The real,
complete version of this logic was already present earlier in the file and
is untouched.

## 3. Real runtime bugs found by turning the compiler back on

Removing the SponsorPortal parse error let TypeScript check the rest of the
project for the first time — it had been silently short-circuiting after
those two fatal errors. 17 more errors surfaced. Most were harmless
(duplicate object keys — see below), but three were genuine runtime bugs:

### 3a. Enrollment monitor task creation crashed on every successful match
(`pages/api/match/index.ts`)

```ts
await db.from('enrollment_monitor_tasks').insert({...}).onConflict('match_result_id').ignore()
```

`.onConflict()` is not a method that exists on the Supabase JS query builder
after `.insert()` — supabase-js v2 requires `.upsert(data, { onConflict, ... })`
instead. This line threw a `TypeError` on **every single successful match**,
which was caught by the surrounding `try/catch` and silently flipped the
`match_results` row to `status: 'error'` — *after* the PDF/email/WhatsApp
notification had already gone out. A coordinator would get "your results
are ready" and then see the job marked failed on the dashboard.

**The fix:** removed the block entirely rather than patching it to use
`.upsert()`. `supabase/migrations/013_fixes.sql` (already in v10-final)
already added a DB trigger (`create_enrollment_monitor_task`, `AFTER UPDATE
ON match_results`) that does this correctly with real SQL `ON CONFLICT`
syntax, backed by a unique constraint that migration also adds. Its own
comment says it was meant as "a safety net" alongside the app-level insert
— in practice, because the app-level insert was broken, the trigger was
the *only* thing that ever worked. Verified by reading that migration in
full and confirming the trigger fires on exactly the transition
(`status → 'done'`) that mattered.

### 3b. Two `.catch()` calls that would throw instead of catching
(`pages/api/abdm/callback.ts`, `pages/api/sponsor/feasibility.ts`)

Supabase's query builder implements `PromiseLike` (has `.then()`) but is
**not a real Promise** — confirmed directly from the installed
`@supabase/postgrest-js@1.15.2` type definitions, which show no `.catch()`
method. Calling `.catch(() => {})` directly on a Supabase call throws
`TypeError: ...catch is not a function` instead of swallowing the error —
in both cases this was inside code whose entire purpose was "don't let this
particular failure become fatal." Fixed by wrapping the `await` in a real
`try/catch`.

### 3c. `nullsLast` isn't a real option (`pages/api/pi-contacts/index.ts`,
`pages/api/site-twins/index.ts`)

`.order('response_rate', { ascending: false, nullsLast: true })` — the real
option (confirmed from the installed type defs) is `nullsFirst`, not
`nullsLast`. This didn't crash — Postgrest just silently ignored the
unrecognised option — but it meant PIs/sites with no `response_rate` yet
were sorting to the *top* of the list (Postgres's DESC default is NULLS
FIRST) instead of the bottom, ahead of ones with an actual known response
rate. Fixed to `nullsFirst: false`, which is what "nulls last" actually
requires when sorting descending.

### 3d. Sign-in page imported a function from a package that doesn't export it
(`pages/auth/signin.tsx`)

`import { signIn, getServerSession } from 'next-auth/react'` —
`getServerSession` isn't exported from `next-auth/react` (only from
`next-auth` itself, server-side). The file already correctly imported and
used it from the right package under an alias two lines below; this was a
dead, wrong duplicate import. Harmless as long as bundling happens to treat
missing named exports as `undefined` rather than throwing, but it's a
genuine `next build` type-check failure regardless, and just wrong code.
Removed.

### 3e. Missing `nodemailer` dependency broke the entire production build

Not caught by `tsc` at all — only surfaced when actually running
`next build`, at the "Collecting page data" stage:

```
Error: Cannot find module 'nodemailer'
Require stack: .../next-auth/providers/email.js → .../pages/auth/signin.js
```

`next-auth`'s `EmailProvider` (used here for magic-link sign-in, with
`sendVerificationRequest` overridden to send via Resend) still requires
`nodemailer` as a real dependency internally, even though this app's own
code never imports it directly. It was entirely absent from `package.json`.
Added `nodemailer@6.9.14`. **This alone would have failed every production
build** — confirmed by reproducing the exact failure on the original
codebase before adding it, and confirming `npm run build` completes cleanly
after.

## 4. Cosmetic-but-real compile errors (duplicate object keys)

Three places set the same object property twice, where JS silently keeps
the last value and drops the first — TypeScript correctly flags this as an
error, but in all three cases here the two values happened to be identical,
so there was no behavioural bug, just dead code and a build failure:
`components/NotificationsPanel.tsx` (`border` set twice), `lib/fhir.ts`
(`'2160-0': 'Creatinine'` listed twice in the LOINC map), `pages/dashboard/
index.tsx` (`borderBottom` set twice in `navLink()`). All three: removed
the redundant first occurrence.

## 5. Stripe / build-blocking type mismatches

- `lib/stripe.ts`: `apiVersion: '2024-04-10'` didn't match what the pinned
  `stripe@16.2.0` SDK's types expect (`'2024-06-20'`) — would not compile.
  Aligned to `'2024-06-20'`.
- `pages/api/billing/webhook.ts`: `Stripe.CheckoutSession` isn't a real
  exported type — the correct nested type is `Stripe.Checkout.Session`.
  Type-only fix, no runtime behaviour change.
- `pages/api/sponsor/engage.ts`: the handler's inferred return type
  (`Promise<void | NextApiResponse>`, from several `return res.json(...)`
  early-exits) didn't satisfy the shared `ApiHandlerFn` type
  (`Promise<void>`). Fixed by prefixing each with `void`, matching the
  idiom `lib/api-handler.ts` already uses internally
  (`return void res.status(...).json(...)`) — no behaviour change, `res`'s
  return value was always discarded by the caller.

## 6. `scripts/seed-site-twins.ts` — missing dependency + interface gap

- `import * as dotenv from 'dotenv'` — `dotenv` was never added to
  `package.json`. Added as a devDependency (`16.4.5`).
- The `SiteRecord` interface never declared `ctri_ids`, even though the
  CTRI-seeding code added later (marked "FIX 5" in the file's own comments)
  reads and writes `s.ctri_ids` throughout. This didn't affect the RPC call
  at runtime (JS doesn't enforce the TS interface), but it meant the script
  didn't type-check — confirmed the actual SQL function
  (`upsert_site_profile` in migration 013) already accepts `p_ctri_ids`
  correctly, so this was a TypeScript-only gap. Added `ctri_ids?: string[]`
  to the interface.
- `sites.size || sites.length` — arrays don't have `.size` (that's a
  Map/Set property); the `||` meant this fell through to `.length` and
  produced the right number at runtime by accident. Simplified to
  `sites.length`.

This script has still never been run against a live database — that
remains true after this pass and needs real Supabase credentials to verify
for real. The fixes here only guarantee it now type-checks and its logic is
internally consistent, not that CTRI's actual HTML export still matches the
parsing assumptions on the day you run it.

## 7. Original 6 issues from the audit

1. **Stale deploy checklist** (`.env.local.example`): said "migrations 001
   through 012" — there are 14 now (13 already existed, 14 added in this
   pass). Rewrote the checklist to say 14, explain why 013 and 014 aren't
   optional, and added a copy-paste RLS-coverage verification query.
2. **`rematch_runs` had no RLS** (the only 1 of 25 tables missing it):
   closed in migration 014. No policies added — only the cron's
   service-role client ever touches this table, so RLS-with-no-policies
   correctly means anon/authenticated get zero access.
3. **ABDM encryption key silent placeholder fallback** (`lib/abdm-client.ts`):
   now throws a clear error if ABDM production credentials
   (`ABDM_CLIENT_ID`/`SECRET`/`HIU_ID`) are set without
   `ABDM_ENCRYPTION_KEY`, instead of silently using a hardcoded placeholder
   string. **Not fully resolved** — see "What's still open" below.
4. **Zero automated tests**: added `vitest`, 8 tests across 2 files, all
   passing. Focused on the matcher fix (highest-severity finding) and the
   HMS import size limit (previously fixed, now locked against regression).
5. **Junk `{pages` packaging artifact**: removed. Confirmed absent from the
   final zip.
6. **Next.js 14.2.3 had a disclosed CVE chain**: confirmed via `npm install`
   deprecation warning, then checked which CVEs actually apply. This app is
   Pages Router only (no `app/` directory, no `middleware.ts`), React 18
   (not 19) — so the severe RCE chain (CVE-2025-55182/83/84/66478/67779,
   which requires App Router + Server Actions) does not apply here.
   Bumped to `14.2.35` anyway as low-risk, in-range insurance, and to stop
   `npm install` flagging it.

## What's still open — not fixed, disclosed instead of glossed over

- **`lib/abdm-client.ts` does not perform real ECDH.**
  `generateECDHPublicKey()` base64-encodes a string and truncates it;
  `decryptHealthBundle()` does not do real decryption either. This was true
  before this pass and is still true now — fixing it properly means adding
  a real Curve25519 implementation (e.g. `tweetnacl`) and is a large enough,
  security-sensitive enough change that it shouldn't be done as a drive-by
  fix without access to ABDM's sandbox to actually test against. What this
  pass did do: make the code fail loudly if production ABDM credentials are
  configured without an encryption key, instead of silently shipping fake
  crypto — and documented the gap in both the code and
  `.env.local.example` so it can't be missed at deploy time. ABDM won't be
  live for months anyway (HIU registration lead time), so there's a real
  window to do this properly rather than rushed.
- **CTRI fetching is still fragile.** It scrapes CTRI's HTML search page
  through a third-party CORS proxy (`api.allorigins.win`) — there's no
  official CTRI API to switch to. This pass made failures *honest* (see #1
  above) rather than *invisible*, but didn't make the underlying fetch more
  reliable. Recommend monitoring server logs for repeated CTRI errors after
  launch.
- **`scripts/seed-site-twins.ts` has never been run against a live
  database** (see #6). It now type-checks; it hasn't been runtime-verified.
- **This pass found real bugs by actually running `tsc`, `vitest`, and
  `next build`.** That's most of why it found things a read-through
  wouldn't have. It's reasonable to assume more exist in code paths that
  aren't yet covered by a test and weren't touched here — the 8 tests added
  cover the matcher fix and the HMS size limit specifically, not the whole
  app.
