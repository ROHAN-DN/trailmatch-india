# FIXES_2026-08-12.md

Pre-deployment verification pass on v17, ahead of a real first deploy
(Tier 0). Everything below was found and fixed by actually running the
code and SQL against real tools — a real local PostgreSQL 16 instance
for the migrations, real `npm`/`tsc`/`vitest`/`next build` for the app —
not by reading and assuming. Every fix was re-verified after the change,
in this same pass, not just written and trusted.

## 1. `npm install` failed without `--legacy-peer-deps`

`next-auth@4.24.15` declares a peer range for `nodemailer` (`^7.0.7`)
narrower than the security-patched version this project actually uses
(`^9.0.4`). Added `.npmrc` with `legacy-peer-deps=true`. Confirmed:
`rm -rf node_modules && npm install` (no flags) now succeeds.

## 2. All 5 Vercel Cron Jobs would have silently never run

`vercel.json` registers `rematch`, `mrr-snapshot`, `data-retention`,
`site-twin-refresh`, and `enrollment-monitor` as native Vercel Cron
Jobs. Confirmed against current Vercel documentation: native cron always
invokes with `GET` + `Authorization: Bearer <CRON_SECRET>`. Every one of
the 5 routes checked only a custom `x-cron-secret` header, and 3 of the
5 additionally rejected anything but `POST` with a 405. As configured,
every real invocation would have failed with 401 or 405 — silently,
since nothing in this project watches Vercel's function logs. One of the
five, `data-retention`, is the DPDP Act storage-minimisation job.

Fix: new `lib/cron-auth.ts`, a shared helper accepting Vercel's real
invocation shape *and* the original header/POST shape (for manual
testing or a Supabase pg_cron alternative). All 5 routes updated to use
it. New test file `lib/__tests__/cron-auth.test.ts` (10 tests) exercises
the exact request shape that was broken.

## 3. `schema.sql` was missing `pgcrypto`

Found by actually running `schema.sql` against a fresh local Postgres
16 database: `gen_random_bytes()` (used for magic-link tokens) is a
`pgcrypto` function, and nothing in this project ever ran
`create extension pgcrypto`. Current guidance on Supabase's own default
extensions is mixed — commonly available, but multiple sources
explicitly instruct manually enabling it — so this isn't guaranteed
pre-enabled on every project. Fixed: `create extension if not exists
pgcrypto;` added to `schema.sql`, alongside the existing `uuid-ossp`
line. Free, idempotent, removes the assumption entirely.

## 4. Migration 011 hard-crashed on every fresh deploy, before this fix

The single most consequential finding of this pass, and only findable
by actually running the full migration chain end to end — reading the
files in isolation, including migration 016's own header comment, gives
an *incomplete* account of the bug.

`schema.sql` always creates a minimal 8-column `audit_log` table.
Migration 011 then declares `CREATE TABLE IF NOT EXISTS audit_log` with
a much richer schema — which is always a silent no-op, since the table
already exists. Migration 016's header comment (accurately) identifies
this much. What it doesn't say: two statements *later in 011's own
script* — a `CREATE INDEX` on `entity_type` and a `CREATE VIEW
org_audit_summary` selecting `outcome` — reference columns that don't
exist yet either, and neither is `IF NOT EXISTS`-guarded the way the
table declaration is. The first one hit throws a **hard SQL error that
aborts the rest of the script in the same run.** Confirmed directly: not
a silent skip, an `ON_ERROR_STOP`-triggering abort.

That means on every deploy that ran 011 as written, everything *after*
that point in the file never executed: RLS was never enabled on
`audit_log`, neither of its two intended policies nor its two
tamper-prevention rules were created, and — the part nothing until now
addressed — the entire `consent_records` table, the DPDP Act §6
consent-tracking table, was never created at all.

Fix, in two parts:
- **`011_audit_log.sql`** — removed the two crashing statements (the
  premature index and the premature view), each replaced with a comment
  explaining why and pointing to the migration that correctly recreates
  it once the underlying column exists (016 for the index equivalent,
  021 for the view). On a truly fresh database, 011 now runs 001→024
  without interruption, and correctly creates `audit_log` (fully), its
  RLS, both policies, both rules, and `consent_records`, in one pass.
- **New `025_audit_log_rls_fix.sql`** — a second, independent finding:
  `schema.sql` separately creates a broad `org_isolation_audit` policy
  on `audit_log` (`FOR ALL`, any org member). Since Postgres RLS
  policies are permissive by default (they OR together), this was never
  actually superseded by 011's much narrower, intentional design
  (admins/owners read-only, service-role insert-only). Confirmed by
  querying `pg_policies` directly after a full migration run: `audit_log`
  had 3 policies, not the 2 migration 011 intends. Practical effect: any
  org member — not just admins — could read the full audit log, and
  could insert fabricated entries directly (the DB-level rules block
  `UPDATE`/`DELETE` but nothing blocked `INSERT`), undermining the
  "tamper-proof, immutable" property 011's own header comment promises.
  025 removes that one policy from `audit_log` specifically (left
  untouched everywhere else, where it's the correct model), and
  idempotently re-applies the rest as a safety net for anyone who
  already ran the pre-fix 011 against a real project.

## 5. New consolidated deploy file: `supabase/00_full_deploy.sql`

Concatenates `schema.sql` → `billing.sql` → `analytics.sql` →
`notifications_and_cron.sql` (tables only) → `billing_analytics.sql` →
`migrations/001` through `025`, in exact order, as one file. Replaces
pasting 30 separate files into the Supabase SQL Editor by hand — a
real, easy-to-get-wrong step for a first deploy.

**This file, exactly as shipped, was run twice against a real local
PostgreSQL 16 instance:** once as a fresh deploy (exit code 0, 45
relations, confirmed `audit_log` ends with exactly the 2 intended
policies by querying `pg_policies` directly), and once again on top of
that already-migrated database, to confirm migration 025 behaves as a
safe idempotent no-op there. Real `pg_trgm`, `pg_cron`, `pgcrypto`, and
`uuid-ossp` were installed for the test. Minimal stubs stood in only for
what a real Supabase project provides natively and nothing else can:
`auth.uid()`/`auth.role()`, the `anon`/`authenticated`/`service_role`
roles, and a no-op `net.http_post()`.

**What this does NOT verify**, honestly: real RLS enforcement under
Supabase's actual PostgREST layer, the `storage` schema, `pg_net` doing
a real HTTP call, or Supabase's exact Postgres point version. That first
real run against an actual Supabase project is still ahead.

## Addendum — Tier 3 security pass (same day)

Queried `pg_policies` directly for every one of the 31 tables in a fully
migrated database — not a re-read of the SQL, an actual query against
what got created — and manually reviewed every policy definition.

- **Confirmed the audit_log fix above holds**: exactly 2 policies, not 3.
- **`rematch_runs` had RLS enabled with zero policies** (migration 014
  turned RLS on, correctly identifying it as the one table missing it,
  but never added a policy). Default-deny, so this was harmless in
  practice — nothing in application code reads or writes this table at
  all (confirmed by exhaustive search; it's dead, like `rxnorm.ts` was
  before it got wired in) — but it would have silently blocked any
  future legitimate use. Fixed in `026_rematch_runs_rls_fix.sql`,
  matching the established `service_role_only` pattern used by
  `mrr_snapshots`.
- **Traced whether the broader RLS breadth on other tables (e.g.
  `org_isolation_users` being `FOR ALL`, allowing any org member —
  not just admins — to update or delete other users' rows if RLS were
  ever the real enforcement boundary) is actually live.** Verified
  directly: the browser never obtains a real per-user Supabase JWT.
  `lib/supabase.ts`'s browser-facing `{ supabase }` export (anon key) is
  never imported anywhere in the app. NextAuth issues its own JWT,
  unrelated to and unrecognized by Supabase's `auth.uid()`. Every real
  data access goes through Next.js API routes using the service-role
  key, which bypasses RLS entirely. **Conclusion: RLS is currently
  defense-in-depth, not the live security boundary — the real boundary
  is the API route layer.** Spot-checked the two highest-leverage
  points there: `pages/api/team/index.ts` (role changes correctly gated
  behind an admin/owner check, and `'owner'` isn't even an assignable
  target role via that endpoint) and `lib/api-handler.ts` (the shared
  wrapper most routes depend on — careful, deliberately-commented
  handling of real edge cases like the MFA-enrollment deadlock). Both
  hold up. The broader RLS permissiveness is real and worth tightening
  eventually as defense-in-depth, but isn't urgent the way the
  `audit_log` conflict was, since that one contradicted its own table's
  explicit design promise regardless of reachability.
