# Fixes — 2026-07-30

The last open item from the original audit: serverless timeout risk in
batch matching (point #5). Previously left as a quantified recommendation,
not a change — this session implements it, carefully, given this is the
most business-critical code path in the app (two production-breaking bugs
were already found and fixed here this month) and it had zero existing
route-level test coverage.

## Batch matching — bounded concurrency instead of strictly sequential

`pages/api/match/index.ts` processed up to 20 patients with a plain
sequential `for` loop — one full match (concurrent CTgov/CTRI/RxNorm
fetches, one Claude API call, PDF generation, storage upload, DB writes)
at a time. The reasoned estimate from the original audit: ~10–15s per
patient realistically, so a full 20-patient batch could land anywhere from
~200s to ~300s — comfortably under the `maxDuration: 300` ceiling in the
typical case, but with little margin, and enough real-world variance
(a few patients hitting Claude retries) to plausibly exceed it.

**What changed**: patients are now processed in chunks of 4, run
concurrently within each chunk, chunks run sequentially relative to each
other. New estimate: ~5 chunks × ~10–15s (bounded by the slowest patient
in each chunk, not the sum) ≈ 50–75s for a full 20-patient batch — roughly
a 4x reduction, leaving the ceiling with real headroom instead of being
uncomfortably close to it. 4 was chosen deliberately conservative — enough
to meaningfully cut wall-clock time without meaningfully increasing load
on CTgov/CTRI/RxNorm's public APIs or risking Anthropic's own per-account
concurrency limits.

**New module**, `lib/concurrency.ts`: a small, generic, independently
testable `processInChunks()` utility — kept separate from the route
handler specifically so the concurrency-limiting logic itself gets real
unit tests, following this project's established pattern of pure logic
living in `lib/`. 11 tests, including one that actually tracks
simultaneously-in-flight workers to prove the concurrency bound is
genuinely honored (not just that results come back correct — a naive
implementation could return correct results while still accidentally
running everything at once).

**A real latent bug found and fixed while restructuring, not introduced
by this change but worse under it**: the original sequential loop's very
first line — the `status: 'running'` update — sat *outside* the
try/catch. A transient DB error there would have aborted the entire
remaining batch, not just that one patient, even before this session's
change. Under bounded concurrency that same gap would be worse — an
uncaught rejection in one patient's processing would reject the whole
`Promise.all` for its chunk, silently orphaning its chunk-mates. Fixed
by moving everything for one patient inside a single try/catch with an
explicit contract: `processOnePatient` now always resolves, never
rejects, regardless of what fails inside it — the same "belt and braces"
pattern already applied this session to cache reads/writes and the rate
limiter.

**Correctness under concurrency, checked deliberately, not assumed**:
- `strongTotal`/`partialTotal`/`failedCount` are only ever mutated in the
  `onChunkComplete` callback, which runs on the main thread between
  chunks (after that chunk's `Promise.all` has already resolved) — never
  concurrently with itself, so no race is possible regardless of how many
  patients just ran in parallel.
- `done_patients` progress is now updated once per chunk instead of once
  per patient (a minor, deliberate granularity tradeoff for a real
  correctness win — no shared counter is read-modified-written from
  multiple concurrent promises).
- Per-patient DB writes (`match_results`, keyed by `patient_id`) don't
  conflict with each other regardless of concurrency — different rows,
  handled independently by Postgres.
- The trial-criteria cache's `upsert(..., onConflict)` (already proven
  safe under genuine concurrent access earlier this session, for the rate
  limiter) means two patients in the same chunk happening to hit a cache
  miss for the same trial simultaneously is safe — at worst, wasted
  duplicate extraction work for that one trial, never data corruption.

Test count: 194 → 205 (+11, all in `lib/__tests__/concurrency.test.ts`).

No route-level test was added for `pages/api/match/index.ts` itself —
consistent with this project's established boundary (nothing in this
codebase tests route handlers directly; the pure logic they depend on is
what gets tested). The concurrency primitive is now thoroughly tested in
isolation; the route handler's correctness rests on that plus careful
manual review, the same level of assurance the rest of this file already
had before this change.
