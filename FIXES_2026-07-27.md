# Fixes & features — 2026-07-27

Starting point: `trialmatch-india-v16-layered-extraction.zip`, confirmed via a
fresh `npm install` + `tsc` (both configs) + `vitest run` + `next build`
+ `node scripts/security-audit.js` to genuinely pass all of its own gates
before any of this work began — 115/115 tests, clean build. This is
that same checkpoint with three things done on top of it.

## 1. Two quick fixes

**`.gitignore` did not exist in this project, in any version, v2 through
v16.** Added one (node_modules, .next, .env*, *.tsbuildinfo, etc.).

**`scripts/security-audit.js`'s auth check had a false positive.** It
flagged 9 real API routes (`sponsor/feasibility.ts`, `export/hms.ts`,
`import/hms.ts`, `prescreening/index.ts`, `prescreening/whatsapp.ts`,
`site-twins/index.ts`, `sponsor/engage.ts`, `sponsor/parse-pdf.ts`,
`sponsor/protocols.ts`) as "missing authentication" because it only
string-matched `getServerSession`/`authOptions` inside each route file
itself. All 9 actually go through the shared `withApiHandler()` wrapper
(`lib/api-handler.ts`), which calls `getServerSession` internally and
401s before the route's own handler runs — one file removed from where
the script was looking. Extended the check to also recognize
`export default withApiHandler(...)`. Verified both directions: the 9
routes now correctly pass, and a deliberately-added fake unauthenticated
route still correctly fails (tested, then removed — not part of the
diff).

## 2. Tier 1 — RxNorm wiring + extractionSource surfaced in the UI

**`lib/rxnorm.ts` was dead code.** Built, unit-tested against mocked
responses, never imported from anywhere else — confirmed by grep before
touching anything. Added `enrichMedicationsWithRxNorm()`, the first real
caller: `lib/matcher.ts`'s `matchPatient` now calls it once per match
(concurrently with the CTgov/CTRI fetches, so no added latency in the
common case), attaching each medication's RxNorm-resolved generic name(s)
and drug-class memberships as two new *optional* fields. Skipped entirely
when a patient has no medications on file — no network call for nothing
to enrich.

`lib/eligibility-rules.ts` (deliberately pure/synchronous/zero-I/O — see
its own header) was extended to read these two optional fields as an
**additive-only** signal: a brand-name record ("Glucophage 500mg") that
plain substring matching cannot connect to a generic-name criterion
("metformin") now can, via RxNorm's resolved name. Same idea for
`medication_class`, additive on top of the existing hardcoded table (a
`RXCLASS_NAME_HINTS` map, explicitly flagged in-code as an unverified
heuristic since this sandbox has no live RxClass access to confirm exact
string formats). Nothing existing can regress: every check that used to
match still matches first; RxNorm can only add a match it didn't already
have.

17 new tests: 7 in `rxnorm.test.ts` for the enrichment function itself
(including "no medications → zero network calls" and "one medication's
failure doesn't affect another's success"), 7 in `eligibility-rules.test.ts`
for the additive matching logic, and 3 end-to-end integration tests in
`matcher.test.ts` proving a patient recorded only as "Glucophage 500mg"
now correctly FAILs a real rule-extracted "no metformin" exclusion
criterion through the actual `matchPatient` flow — not just at the
isolated unit level.

**`extractionSource` existed in the data model, was unit-tested, and was
invisible in the UI** — confirmed by grep, zero references in any
component. Root cause, found while fixing it: two different `TrialMatch`
interfaces had drifted apart. `lib/matcher.ts` has its own local
`TrialMatch` (includes `deterministicResults`, the field with
`extractionSource`); `lib/types/domain.ts`'s shared `TrialMatch` (which
`components/MatchExplainability.tsx` actually imports) didn't declare
that field at all. The JSON was already flowing all the way to
`match_results.matches` in Postgres and back out over the API — the
frontend just couldn't type-check accessing it. Extended the shared type,
then rewrote `MatchExplainability.tsx`'s criteria rendering into three
real tiers (RULE-BASED / AI-EXTRACTED / AI INTERPRETATION) instead of the
old binary VERIFIED/unmarked split, with a legacy fallback for
already-stored rows that predate the field.

**Caught a real bug in my own first draft before it shipped**: a
prefix-string filter (`!text.startsWith('✓ Verified — ')`) intended to
isolate the model's genuinely-interpreted judgment doesn't work —
`lib/matcher.ts`'s deterministic-but-UNKNOWN results are deliberately
built *without* that prefix, identical in shape to a real interpreted
entry, so the filter would have double-rendered them, mislabeled as "AI
INTERPRETATION." Replaced with a position-precise split
(`interpretedOnlyEntries()`, exported and unit-tested directly, since this
project has no React component-testing setup and adding one for a single
pure function would be scope creep).

## 3. Tier 1 — Trial-criteria cache (the big one)

This is the feature described in the pasted conversation as interrupted
mid-build by a sandbox filesystem reset, never recovered, checkpointed
back to v16 before it existed. Rebuilt from scratch against this
checkpoint, using the design already described there as a starting point.

**New migration**, `018_trial_criteria_cache.sql`: a `trial_criteria_cache`
table keyed by `(source, trial_id)` **plus** a sha256 hash of the exact
eligibility text criteria were extracted from — not trial ID alone. A
protocol amendment that changes a trial's eligibility text produces a
different hash, so the next match against it is a genuine miss
(re-extract, overwrite) rather than a cache silently serving criteria
that no longer match the live protocol. Deliberately not org-scoped —
a trial's eligibility criteria are a fact about the trial, not about
whichever org is matching against it; two hospitals matching the same
NCT ID should share one cached answer, not pay to extract it twice. RLS
follows the same read-all-authenticated/service-write-only shape already
established by `india_site_profiles` (migration 006).

**Found and fixed a second, unrelated real bug while reading migration
conventions**: migration 002's trigger calls `update_updated_at()`, but
that function was never defined anywhere in any of the 17 migrations —
confirmed by grep. Running migration 002 for real against a fresh
Postgres database would fail exactly there with "function does not
exist," which would also block every migration after it, including the
new one this session adds. Fixed with a minimal, self-contained
definition at its first real use.

**`lib/trial-criteria-cache.ts`**: a store abstraction (same "pass the
client in" pattern as `lib/clinical-data.ts` and `lib/ratelimit.ts`), two
implementations — in-memory for tests, Supabase-backed for production.
Both `get()`/`set()` are built to never throw: a read failure degrades to
a miss, a write failure is logged and swallowed. A cache being down
should make matching slower, never break it.

**`lib/matcher.ts` rewired**: `scoreWithClaude`/`matchPatient` now check
the cache per retrieved trial before extraction. On a **hit**, the prompt
tells Claude the criteria for that trial are already final — don't
extract, don't duplicate — and gives it the full eligibility text only as
context for judgment calls on anything not already covered. On a
**miss**, falls back to the original rule-based-extraction flow exactly
as it worked before this feature, and the final merged criteria (rule-based
+ whatever Claude extracted from the residual) get written back to the
cache. Dedup and `extractionSource` tagging both correctly handle
cache-recovered criteria, not just freshly-extracted ones — a criterion's
"rule-" ID prefix survives the JSON round-trip through storage, so its
original source is recovered without needing separate bookkeeping. Added
explicit defense-in-depth `.catch()` wrapping around every cache
read/write call site in `matcher.ts` itself — even if some future store
implementation doesn't honor its own "never throws" contract, a cache
failure still can't take down a match.

**Wired into both real callers**: `pages/api/match/index.ts` (constructs
the store once per request, reusing the existing `supabaseAdmin()`
client already in scope) and `lib/rematch.ts`'s `rematchPatient`
(constructs it the same way `readStructuredClinicalData` already gets its
client, right where the transcript said it would). `matchPatient`'s new
third parameter is optional — any caller that doesn't pass it behaves
exactly as before this feature existed, always a miss, zero caching
attempted. Verified explicitly with a dedicated test.

23 new tests: 18 for `lib/trial-criteria-cache.ts` directly (hash
stability/invalidation, hit/miss, source+trial-ID disambiguation, graceful
degradation on DB errors, malformed cached data, and synchronous throws
from a broken client), and 5 end-to-end integration tests through
`matchPatient` — a genuine miss extracts and writes; a second match
against identical trial text is a real hit (verified by inspecting the
actual prompt text sent to Claude, not just the output); a hit never
re-writes the cache; a changed eligibility text is correctly treated as a
fresh miss with both old and new criteria present; and — deliberately
tested for — if Claude disobeys the "don't re-extract" instruction on a
hit, the duplicate is dropped, not double-counted.
