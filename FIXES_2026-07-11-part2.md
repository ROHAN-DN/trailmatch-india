## 1. Real ECDH implemented in `lib/fidelius.ts` (new file)

The previous placeholder (`generateECDHPublicKey`/`decryptHealthBundle`)
base64-encoded a string and called it a key. It's been replaced with an
actual implementation of ABDM's "Fidelius" protocol: Curve25519 in
BouncyCastle's **Short Weierstrass form** (confirmed to NOT be the same as
standard Montgomery-form X25519 — libraries like `tweetnacl` would not have
interoperated), HKDF-SHA256 key derivation, AES-256-GCM.

**How this was verified, without any live ABDM access:**
1. The curve constants (a, b, order, cofactor) were read directly from the
   primary source — `bcgit/bc-java`'s `Curve25519.java` — not copied from a
   blog's claim about them.
2. The field prime and generator point were checked with actual modular
   arithmetic run in this session (Python): confirmed `p == 2^255 - 19`,
   and confirmed the generator point satisfies `y² = x³ + ax + b (mod p)`
   using those exact verified `a`/`b` values.
3. `dimagi/pyfidelius` — a real, maintained, open-source Python reference
   implementation of this exact protocol — was installed and run directly
   from its actual source in this session. It reproduced a test vector
   published independently by an unrelated blog, byte-for-byte.
4. This file's TypeScript implementation (different language, different EC
   library — `elliptic`/`bn.js` vs. Python's `fastecdsa`/`pycryptodome`)
   was checked against that same test vector and produces **identical
   ciphertext**. Locked in as a regression test in
   `lib/__tests__/fidelius.test.ts`.
5. Additionally fixed a real gap in the reference implementation rather
   than copying it: `pyfidelius`'s decrypt calls PyCryptodome's
   `cipher.decrypt()`, which does **not** verify the GCM auth tag. This
   implementation always verifies (`decipher.setAuthTag()` +
   `.final()`, which throws on mismatch) — confirmed by a test that
   tampers with ciphertext and asserts decryption is rejected, not
   silently garbled.

**What this does NOT establish:** that it interoperates with ABDM's actual
live gateway. Three independent implementations agreeing is strong evidence
the algorithm is implemented correctly; it is not the same as a real
end-to-end test against `sandbox.abdm.gov.in`, which this environment
cannot reach. This needs to be run against the real ABDM sandbox before any
real patient's health data flows through it — flagged explicitly in
`.env.local.example`'s ABDM checklist.

**Integration changes required beyond the crypto itself:**
- `requestHealthInfo()` now generates a fresh ephemeral keypair + nonce per
  session and returns it — the caller must persist it (there was
  previously no state management for this at all, because the placeholder
  didn't need any).
- Added migration `015_fidelius_keys.sql`: three new columns on
  `abdm_sessions` (`fidelius_private_key`, `fidelius_public_key_x509`,
  `fidelius_nonce`) to store this between the request and the callback.
- `pages/api/abdm/verify.ts` now persists the returned key material.
- `pages/api/abdm/callback.ts` now passes the session's stored key material
  plus the HIP's public key/nonce from the callback payload into the real
  `decryptHealthBundle()`.
- `ABDM_ENCRYPTION_KEY` env var removed everywhere (`.env.local.example`,
  `supabase/abdm_setup.md`) — no longer applicable, since key generation is
  now per-session and ephemeral rather than a static server-wide secret.

## 2. CTRI/ClinicalTrials.gov fetch resilience (`lib/matcher.ts`)

Added a retry-with-backoff helper (`fetchWithRetry`) used by both fetch
functions: one retry with a short fixed backoff, skipped for non-transient
4xx errors (a bad request won't succeed on retry) or 429/5xx (which will).
Verified with 3 new tests: recovers from a single transient failure,
correctly reports `error` status only after retries are exhausted (not on
the first failure), and does not waste a retry on a plain 4xx.

Also added a distinct server-side log line when a CTRI fetch succeeds at
the HTTP level but parses zero rows from non-trivial HTML — a leading
indicator that CTRI's page markup changed and the regex parser silently
broke, as opposed to a genuine zero-result search. This doesn't change
what a coordinator sees (still an honest "no results" per the previous
fix) — it's for server-side monitoring, so this failure mode doesn't stay
invisible if it happens.

**What this does not fix:** CTRI still has no official API; this is still
HTML-scraping through a third-party proxy (`api.allorigins.win`), which
remains a fundamentally fragile approach. Retries reduce false negatives
from transient blips; they don't make the underlying scrape robust to
CTRI changing its page structure.

## 3. `scripts/seed-site-twins.ts`

**What could actually be verified:** the pure parsing/classification logic,
with 20 new tests in `scripts/__tests__/seed-site-twins.test.ts` using
fixture data (`classifySiteType`, `inferSpecialties`, `parseCTRICsv`,
`mergeStudiesIntoSiteMap` — all now exported specifically so they're
testable). This is a real, narrower guarantee than "this script works,"
and that distinction is deliberate, not a hedge.

**What that testing effort found — two more real bugs:**

- **The CTRI CSV parser used a naive `line.split(',')`.** This breaks on
  any quoted field containing a comma — not a theoretical edge case: CTRI
  institution names routinely include one, e.g. "All India Institute of
  Medical Sciences, New Delhi" would have been truncated to "All India
  Institute of Medical Sciences" with every subsequent column shifted by
  one. Fixed by using `papaparse` (already a dependency, already used
  elsewhere in this codebase for the HMS CSV import) instead of hand-rolled
  splitting. A test with exactly this comma-in-institution-name case is
  now locked in.
- **`main()` executed unconditionally at module load, with no
  `require.main === module` guard.** This meant simply importing this
  file's pure functions to write the tests above would have triggered a
  real seeding run — live requests to ClinicalTrials.gov/CTRI and live
  writes to Supabase — as a side effect of importing it. Found by actually
  trying to write the test, not by inspection. Fixed with the standard
  CommonJS guard (confirmed correct via the project's `tsconfig.scripts.json`,
  which sets `module: commonjs`). Applied the identical fix to
  `scripts/seed-pi-contacts.ts`, which had the same pattern (an
  unconditionally-executing IIFE at module load).
- **Smaller, found the same way:** `inferSpecialties`'s Metabolic keyword
  list contained `'diabetes'` but not `'diabetic'` — meaning a trial titled
  "Diabetic Nephropathy" or "Diabetic Retinopathy" (both common,
  real-world condition names) would not have been tagged Metabolic at all.
  Fixed by using the shared root `'diabet'`, confirmed to match both forms.

**What remains genuinely unverified:** this script has still never been run
against a live Supabase database or live ClinicalTrials.gov/CTRI endpoints.
The fixes above make its logic demonstrably correct against realistic
fixture data and guarantee it no longer executes accidentally on import —
they do not confirm CTRI's current live CSV export still has the column
names this code expects, or that the `upsert_site_profile` RPC call
succeeds against a real database. That can only be confirmed by running it
for real, which needs real Supabase credentials this environment doesn't
have.
